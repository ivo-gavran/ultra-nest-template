# Users persistence and passwords

PR-05 adds `UsersModule` under `src/modules/users/`. `AppModule` imports it, and other features can import it to inject `UsersService` or `PasswordsService`. There are no controllers, login/registration routes, tokens, sessions or authorization policies in this milestone. The authentication package's module is not registered; only its `PasswordHasher` provider is instantiated.

## Service contract

| Method                                      | Result                                                                   |
| ------------------------------------------- | ------------------------------------------------------------------------ |
| `create({ email, password, displayName? })` | Persisted `PublicUser`, always with the default `user` role              |
| `findById(id)`                              | `PublicUser` or `undefined`                                              |
| `findByEmail(email)`                        | `PublicUser` or `undefined`; same email normalization as writes          |
| `update(id, { email?, displayName? })`      | Updated `PublicUser` or `undefined`; at least one defined field required |

Create/update inputs and the public model use `z.infer` from `src/modules/users/schemas/user.schema.ts`. The service validates inputs at runtime too. IDs must be UUIDs. Invalid values raise Zod validation errors; callers should use `try`/`await`/`catch` because validation can also fail before a promise is returned.

Email is trimmed, lowercased, limited to 254 characters and validated with Zod's email format. No provider-specific transformations such as removing dots or plus suffixes are applied. Display names are trimmed and limited to 1–100 characters when present. Omission at creation stores `null`; setting `displayName: null` clears it on update. Empty strings are rejected.

Both create and update schemas are strict. Callers cannot set `role`, `id`, `passwordHash` or timestamps. Updates accept only email and display name; password changes belong to a later account lifecycle operation with session revocation. The PostgreSQL enum supports `user` and `admin`, but this feature exposes no privileged role-assignment method. Future HTTP adapters must enforce authenticated identity and permissions before invoking persistence operations.

`PublicUser` contains `id`, `email`, `displayName`, `role`, `createdAt` and `updatedAt`. Timestamps are JavaScript `Date` objects at this internal service boundary. The repository uses explicit projections for every select/returning query, so a password hash is never loaded into ordinary return objects. The strict public schema also rejects credential-bearing objects. Raw Drizzle row/insert types stay separate from the public shape; the module does not export `UsersRepository`.

## Database behavior and errors

Run `pnpm db:migrate` before calling the service. `0001_users.sql` adds a UUID primary key generated by PostgreSQL, normalized email, password hash, nullable display name, default `user` role and timezone-aware creation/update timestamps. The migration leaves the existing example table and data intact. Migrations remain an explicit deployment step.

The unique index on `lower(email)` rejects duplicates even for mixed-case direct SQL writes and concurrent inserts. The service does not perform a racy existence check before inserting. Conflicting creates or email updates raise `UserEmailConflictError`, with no email or SQL details in the error. Other database failures become `UserPersistenceError`; original Drizzle errors and causes are deliberately discarded because their query parameters can contain hashes. No persistence inputs or hashes are logged.

Creation timestamps use database defaults. Repository updates explicitly set `updatedAt` with PostgreSQL `statement_timestamp()` and preserve `createdAt`. There is no trigger: future direct SQL mutations must also maintain the update timestamp. A missing user produces `undefined` on lookups/updates. These are internal service outcomes; HTTP status mapping belongs to the future API layer.

## Password utilities

The exact PR-00 version `@nestjs/authentication@0.1.1` supplies `PasswordHasher`. `PasswordsService.hash()` validates passwords, then delegates to the package. `verify()` delegates directly, including its handling of absent or malformed stored hashes. No custom cryptography or plaintext password persistence is introduced.

Accepted new passwords have 12–128 JavaScript string code units, are not trimmed, and must fit the package's 4096-byte limit after NFKC normalization. The package owns normalization, random salts, encoded hash formatting and verification. The provider uses its production defaults: scrypt `logN=17`, `r=8`, `p=1`, a 16-byte salt and a 32-byte derived key. Each concurrent derivation requires approximately 128 MiB for scrypt; budget memory and libuv threadpool concurrency before exposing password operations to traffic. Rate limiting and authentication endpoints remain later milestones.

The password suite executes a real hash and correct/incorrect verification at production defaults. Other password tests and the users integration suite override the hasher to `logN=10` only in test code to keep concurrency tests cheap. Production configuration has no reduced-cost override.

## Verification

Run `pnpm test` for schemas and password utilities. With Docker running, run `pnpm test:integration` for the real PostgreSQL migration and persistence tests. Run these sequentially because both rebuild `.test-dist/`. The integration suite covers creation, lookups, updates, role constraints, case-insensitive email uniqueness (including direct SQL and concurrent service calls), sensitive-field omission, rejected mass assignment, sanitized errors and migration upgrades preserving existing records.

See [PR-05 verification](pr-05-verification.md) for exact results. API verification remains covered by the existing application tests and Docker smoke test.
